## Context

See `proposal.md` for motivation and scope. Foundation already owns OS directories, file logger, SQLite, loopback HTTP, readiness-before-browser and signal/context shutdown in `internal/app`. This change must add runtime ownership without replacing those paths or requiring a Kiwix installation on an empty profile. Source authority is `docs/main-spec.md` §§7–8/17/20–22 and change 02.

At initial planning, `kiwix-serve` was not installed. Its official CLI source at commit `4717ee15faa77c9e9641557b85af19f1fad5ea27` and official HTTP docs were read during planning. They define `--address`, `--port`, foreground operation by omitting `--daemon`, positional ZIM paths and a welcome page at `/`; no Kiwix `/health` endpoint is assumed. Subsequent Linux smoke with Kiwix 3.8.2 and a small valid ZIM established ordinary CLI/lifecycle compatibility, but independent review reproduced false readiness against an unrelated HTTP listener (3/3) and Stop blocked by restart readiness (2/2). This revision refines the existing startup/shutdown guarantees to resolve those failures. The current upstream also supports directories, but this change only needs explicit file-path inputs so it does not silently become package discovery.

## Goals / Non-Goals

**Goals:** A small callable Go lifecycle boundary backed by a real process manager; deterministic ownership, readiness and failure semantics; actual app cleanup integration; process-fixture evidence.

**Non-Goals:** No generic supervisor/process-driver framework, persistence of PID/state, registry scanning, public runtime API, proxy endpoint, frontend feature or release layout implementation. Resolving an adjacent runtime executable defines a future-compatible location without bundling it. Local content paths are opaque process inputs; checking that a supplied path is a readable local file is not ZIM parsing or install validation.

## Decisions

### 1. Minimal interface and package ownership

Use one `ContentProvider` interface under `internal/providers` with only `EnsureStarted(context.Context) error`, `Stop(context.Context) error`, `Restart(context.Context) error`, and `Status() RuntimeStatus`. Their immediate consumers are app start/cleanup and lifecycle recovery/status tests; restart/status fulfill source02's explicit lifecycle requirements. `RuntimeStatus` is a value snapshot containing state, live PID and last diagnostic; it carries no public URL or content metadata. No `ID`, catalog, download, search, capability negotiation or open/read placeholder is needed now.

The sole concrete `KiwixProvider` in `internal/providers/kiwix` delegates process details to a small Kiwix runtime implementation (`internal/runtime/kiwix` is appropriate). Kiwix arguments, executable resolution and readiness belong there; app orchestration knows the interface. Constructor options accept executable override, explicit local `ZIMPaths` and log/output sinks. These are concrete Kiwix inputs, not generic interface parameters. A compile-time interface assertion and tests exercise the actual implementation. Do not add future provider stubs or a registry/factory to choose among nonexistent providers.

### 2. Lazy resolution and empty-profile integration

Add `--kiwix-binary <path>` as a development-only override passed through app options to the concrete provider. Resolve a relative explicit path to an absolute path against the invocation working directory once; preserve spaces as part of the path and report invalid overrides without fallback. Without override, use `os.Executable` (resolving executable symlinks where available) and the adjacent `runtime/kiwix-serve` or `runtime/kiwix-serve.exe`. Do not search arbitrary working-directory binaries or silently fall back to PATH. Missing/non-executable/directory/OS execution errors retain context. Resolution happens only for nonempty content startup, so an override can be absent or invalid without disrupting an empty shell.

The normal app constructs and owns one Kiwix provider with no content inputs in this change. `EnsureStarted` is then a stopped-state no-op and does not inspect the binary. There is no fake content, environment-specific auto-discovery or forced empty-library launch. A narrow app option/dependency seam permits an injected real provider in integration tests; this is already used by this change and must not become a general dependency framework. Later change06 supplies installed content inputs through this boundary. A development ZIM CLI, SQLite content registry, filesystem scan and always-on runtime are unnecessary for change02.

After DB setup, register provider cleanup immediately and call ensure-start before opening the browser. For a configured test/integration provider, startup error returns a contextual visible app error via existing stderr/log handling and acquired resources are cleaned. Browser is never opened after failed startup. After successful startup, an unexpected runtime exit updates state and logs without taking down the shell. No runtime diagnostic is added to `/api/health`, whose exact foundation JSON stays intact.

### 3. Command, port and readiness

Launch with `os/exec` and distinct arguments equivalent to `kiwix-serve --address=127.0.0.1 --port=<selected> <absolute-zim-path>...`. Never use a shell or `--daemon`; pass local paths as positional arguments, not interpolated command strings. Absolute paths prevent a leading filename dash from being interpreted as an option. No public/configurable bind address is offered.

Select an unused IPv4 loopback port with a short-lived `127.0.0.1:0` listener, close it immediately before starting Kiwix, then probe only that internal address. Kiwix does not inherit this listener, so another ordinary process can win the handoff while the child is still doing startup work. A live child plus HTTP 200 for a fixed interval cannot establish ownership; increasing an observation delay cannot fix this. Never adopt or kill an existing listener. A bounded retry (at most three fresh-port attempts) is allowed only after failed owned-child cleanup for a detected collision; otherwise return the failure. There is no infinite retry.

Use narrow private platform helpers inside the Kiwix runtime to prove that the exact started child PID owns a TCP LISTEN socket on the selected `127.0.0.1` IPv4 address and port. On Linux, correlate `/proc/<child-pid>/fd` socket-inode links with listening IPv4 TCP records in that child's network namespace (for example `/proc/<child-pid>/net/tcp`); a TCP-table row alone does not prove PID ownership. On Windows, query `GetExtendedTcpTable` for IPv4 PID-owner listener rows and match the selected address, port and exact child PID. These helpers answer only this startup ownership question; do not build a generic socket/process inventory framework or expose a public API. Keep the owned process handle and generation authoritative; these reads never authorize terminating a foreign PID.

Readiness requires bounded `GET /` returning HTTP 200, positive exact-child listener proof, and the owned foreground child still alive with no winning cancellation, within a default 10-second startup deadline and a short per-request timeout. Recheck ownership/liveness/cancellation before publishing ready so a stale observation cannot complete a stopped generation. Disable HTTP proxies and redirect following, close response bodies and bound any reads; do not parse Wikipedia content or depend on a specific HTML body. Polling observes exit/cancellation alongside HTTP and ownership. Missing, unreadable or mismatched ownership evidence never qualifies as ready: retry observation only within the startup deadline, then fail closed with contextual diagnostics and owned cleanup. Do not infer ownership/readiness from process creation, a bare TCP accept, stdout text or elapsed time. Startup context bounds startup only; app lifetime owns the subsequent explicit stop. Technical selected-address logs are allowed; the address is not placed in app URL, API JSON, browser output or UI. No public endpoint getter is needed until serving integration.

Regression evidence must include a child delayed 500 ms before bind and an unrelated listener already returning HTTP 200 well before that bind. Startup must not return success from the unrelated response; failure/bounded retry must reap the failed owned attempt and preserve that listener. Also cover positive owned-listener detection and unavailable/mismatched ownership evidence.

### 4. State, concurrency and reaping

States are `stopped`, `starting`, `ready`, `stopping`, `failed`. No-content ensure preserves `stopped`; successful start clears the previous error. PID is set only after `cmd.Start` succeeds and cleared after process completion. Unexpected exit from starting/ready becomes failed even for exit status 0; deliberate stop/cancellation becomes stopped. Last-error/exit diagnostics survive a failure long enough for callers/logs to inspect. Keep status in memory only, never trust a saved PID to recover a process.

Serialize mutating lifecycle operations while allowing Stop to publish stop intent and cancel an in-progress readiness wait promptly, including replacement readiness inside Restart. Do not hold a serialization mutex over readiness if that prevents Stop from publishing/cancelling, or requires Stop to wait for the startup timeout before observing its own context. The implementation may publish cancellation before acquiring operation serialization or narrow that serialization; choose the smallest synchronization change preserving the invariants below.

Concurrent ensure callers share one attempt and result; a ready instance returns without spawning. A caller cancelling its own wait must not create a replacement or abandon cleanup; the initiating startup cancellation cancels that attempt. Once Stop wins, the earlier attempt and any already queued/in-flight restart cannot publish ready, report replacement success or spawn a late generation. A later explicit startup request after completed Stop may start normally. Explicit restart performs full stop/reap followed by ensure with the same immutable concrete inputs. Stop during delayed or never-ready replacement startup must cancel that replacement and complete bounded cleanup without waiting for its readiness deadline. A short or already-cancelled Stop context must still publish stop intent and must not leave the owned child running merely to return a context error; retain a bounded termination/reap path. Restart after failure is supported; autonomous restart and background retry loops are not.

Each started child has exactly one wait/reap owner and a completion signal used by readiness, stop and restart; do not call `Wait` independently from multiple paths. Do not hold a status lock while waiting for exit or draining output. A completed old generation cannot overwrite a newer child's status. Use actual process fixtures and race detection to verify these invariants rather than exposing synchronization hooks as product API.

### 5. Shutdown and diagnostics

Register shutdown so HTTP closes, provider stop finishes, SQLite closes, then log file closes; startup rollback also reaches provider cleanup. Use a fresh bounded shutdown context rather than the already-cancelled app context. On Linux send SIGTERM to the owned foreground process, allow a short grace period (default two seconds), then kill if necessary. On Windows use direct owned-process termination because portable Go process interrupt is not a reliable graceful signal there. In both cases wait/reap and finish output draining before returning; cleanup failure is logged and returned/combined with any existing error instead of silently discarded. Stop on an absent/already-exited child is successful and idempotent. Never kill by executable name, port, stale PID or process search. Kiwix foreground mode has no daemonized descendant to track; arbitrary process trees and abrupt parent SIGKILL survival are not this change's guarantee.

Capture stdout and stderr separately into draining writers or bounded readers connected to the existing logger, with explicit stream labels. Use fixed-size chunks or capped line assembly (for example 4 KiB chunks and at most 64 KiB retained diagnostic tail per stream), truncate retained tails, and do not rely on an unbounded `bytes.Buffer` or default `Scanner` line limit. Output drains continue even when retention truncates, so a long line or both streams filling cannot block cleanup. No new persistent logging/rotation subsystem is needed. Lifecycle errors contain operation context, and the log records executable/start/selected internal address, ready, exit result, restart and stop. Do not log content bodies.

## Risks / Trade-offs

- Port selection cannot be atomic across a separate executable → exact-child listener ownership proof plus bounded HTTP readiness, cancellation/exit observation and bounded collision handling. Ordinary delayed-bind collisions are in scope; broad hostile same-user attacks and authenticated local endpoints are outside this guarantee.
- Linux ownership proof requires mounted/readable procfs entries for the application's own child and its network namespace → document this runtime assumption and fail closed with cleanup if proof is unavailable; do not silently weaken readiness to HTTP/liveness. Windows uses its native PID-owner TCP table API; parsing/unit evidence and cross-build are not native execution evidence.
- HTTP 200 proves runtime HTTP availability, not ZIM correctness/search/article functionality → later content verification/serving changes own those contracts; optional real smoke only claims what it executes.
- Linux signal semantics differ from Windows → platform-specific stop helpers and Windows cross-build; native Windows lifecycle execution remains explicitly unverified unless actually run.
- Synchronous log sinks can be slow → bounded in-memory retention and independent draining; test long concurrent streams and do not hold lifecycle locks over output processing. A permanently stalled external sink is outside ordinary local-file logging guarantees.
- No installed-content activation yet → empty shell remains usable and real runtime path is exercised through explicit constructor inputs and app integration fixtures, with later change06 owning installed-package activation.

## Migration Plan

No schema migration or user-data reset is required. Existing foundation directories remain authoritative; runtime state is in memory, and no new writable data is placed beside the executable. New code can be rolled back without changing existing DB/content. Build artifacts and fixtures stay outside committed user data. Packaging/bundling and supported upstream version selection remain release work; real smoke records the actual version used rather than claiming compatibility with every Kiwix release.
